# Init

Init-системы: первый процесс, который запускается при загрузке Linux, и три поколения подходов к нему — SysV, Upstart, systemd.

---

## 1. System V Overview — Обзор System V

`init` — это самый первый процесс, который запускает ядро после загрузки (PID всегда `1`). Он порождает все остальные процессы системы и следит за их состоянием. **System V init (SysV)** — классический, самый старый подход к этому, пришедший из Unix.

```bash
ps -p 1

```

```
Вывод: PID 1 — процесс init (или его преемник)

```

- SysV работает через понятие **runlevel** (уровень выполнения) — пронумерованные режимы работы системы (0 — выключение, 1 — однопользовательский режим, 3/5 — обычная многопользовательская работа с сетью/GUI, 6 — перезагрузка)
- Скрипты для каждого runlevel лежат в `/etc/init.d/`, а на нужный runlevel их подключают через символические ссылки в папках `/etc/rcN.d/`
- Главный минус SysV — скрипты запускаются **строго последовательно**, один за другим, что делает загрузку медленной

```bash
runlevel # Показать текущий и предыдущий runlevel
sudo init 3 # Переключиться на runlevel 3

```

---

## 2. System V Service — Управление сервисами в SysV

Каждая служба (сервис) в SysV — это скрипт в `/etc/init.d/`, который принимает стандартные аргументы: `start`, `stop`, `restart`, `status`.

```bash
sudo /etc/init.d/apache2 start

```

```
Вывод: служба apache2 запущена

```

```bash
sudo service apache2 status # Обёртка над /etc/init.d/, работает одинаково на разных дистрибутивах
sudo update-rc.d apache2 defaults # Добавить сервис в автозапуск на стандартных runlevel'ах
sudo update-rc.d apache2 remove # Убрать сервис из автозапуска

```

- `service` — универсальная команда-обёртка, которая под капотом вызывает нужный скрипт из `/etc/init.d/`
- Сам скрипт службы обычно содержит функцию для каждого действия (`start`, `stop`) и логику проверки, запущен ли процесс уже (через PID-файл)

---

## 3. Upstart Overview — Обзор Upstart

**Upstart** — init-система, разработанная в Ubuntu как замена SysV. Главная идея — переход от строгой последовательности runlevel'ов к запуску служб **по событиям** (event-based).

```bash
initctl version

```

```
Вывод: init (upstart X.X)

```

- Вместо "сначала runlevel 2 полностью, потом runlevel 3" Upstart реагирует на события: "диск смонтирован", "сеть поднялась", "сервис X запустился" — и параллельно запускает то, что от этих событий зависит
- Это ускоряет загрузку — независимые службы стартуют одновременно, а не по очереди
- Upstart всё ещё сохранял частичную совместимость со скриптами `/etc/init.d/` для плавного перехода

---

## 4. Upstart Jobs — Задания Upstart

Каждая служба в Upstart описывается конфигурационным файлом задания (**job**) вместо shell-скрипта.

```bash
cat /etc/init/ssh.conf

```

```
Вывод: конфиг задания — секции start on, stop on, exec

```

Ключевые секции job-файла:

```
start on <событие> # При каком событии запускать (например, "started network")
stop on <событие> # При каком событии останавливать
exec <команда> # Какую программу фактически запускать
respawn # Перезапускать процесс автоматически, если он упал

```

```bash
sudo start ssh # Запустить задание
sudo stop ssh # Остановить задание
sudo status ssh # Посмотреть статус
initctl list # Показать все задания и их состояние

```

- Декларативный конфиг вместо скрипта — проще читать и писать, чем полноценный shell-скрипт SysV

## 5. Systemd Overview — Обзор systemd

**systemd** — современный стандарт init-системы, используется в большинстве актуальных дистрибутивов (Ubuntu, Debian, Fedora, RHEL/CentOS, Arch и др.), полностью заменив и SysV, и Upstart.

```bash
systemctl --version

```

```
Вывод: systemd 245 (245.4-4ubuntu3.15)

```

- Службы описываются **unit-файлами** (`.service`, `.socket`, `.mount`, `.target` и другие типы)
- Управляется через единую команду `systemctl` вместо разрозненных инструментов
- Умеет запускать службы параллельно и "лениво" — например, по факту первого обращения к сокету, а не сразу при загрузке (socket activation)

```bash
systemctl start nginx # Запустить службу
systemctl stop nginx # Остановить
systemctl restart nginx # Перезапустить
systemctl status nginx # Посмотреть статус
systemctl enable nginx # Добавить в автозагрузку
systemctl disable nginx # Убрать из автозагрузки

```

---

## 6. Systemd Goals — Цели systemd (targets)

В systemd понятие runlevel заменено на **target** — именованную точку, объединяющую набор unit'ов, которые должны быть активны для достижения этого состояния системы.

```bash
systemctl get-default

```

```
Вывод: graphical.target

```

Соответствие старых runlevel новым target (для совместимости):

```
runlevel 0  →  poweroff.target   (выключение)
runlevel 1  →  rescue.target     (однопользовательский режим)
runlevel 3  →  multi-user.target (многопользовательский, без GUI)
runlevel 5  →  graphical.target  (многопользовательский + графическая оболочка)
runlevel 6  →  reboot.target     (перезагрузка)

```

```bash
systemctl isolate multi-user.target # Переключиться на конкретный target
sudo systemctl set-default multi-user.target # Задать target по умолчанию при загрузке
systemctl list-units --type=target # Показать все доступные target'ы

```

- Target'ы могут зависеть друг от друга — например, `graphical.target` требует, чтобы сначала был достигнут `multi-user.target`
- Задача systemd при загрузке — не "пройти по номерам", а разрешить граф зависимостей и достичь целевого target максимально параллельно

## 7. Power States — Состояния питания

systemd управляет и переходами системы между состояниями питания через ту же команду `systemctl`.

```bash
systemctl poweroff

```

```
Вывод: система выключается

```

```bash
systemctl reboot # Перезагрузка
systemctl poweroff # Полное выключение
systemctl suspend # Спящий режим (Suspend to RAM) — состояние хранится в оперативной памяти, быстрый выход
systemctl hibernate # Гибернация (Suspend to Disk) — состояние сохраняется на диск (в swap), питание можно полностью снять
systemctl hybrid-sleep # Гибрид: и в RAM, и на диск одновременно — на случай, если разрядится батарея во время suspend

```

- **Suspend** — самый быстрый способ "заморозить" систему, но требует постоянного питания для RAM (разрядится батарея — данные потеряются)
- **Hibernate** — медленнее засыпает и просыпается, зато не требует питания вообще, состояние читается обратно с диска при включении
- **Hybrid-sleep** — компромисс: быстрый выход как у suspend, но с подстраховкой hibernate на случай отключения питания
